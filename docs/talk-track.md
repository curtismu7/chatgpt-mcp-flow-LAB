# Talk track (about 9 minutes)

Goal: leave the room able to say why an AI assistant can call a private tool for a user without ever holding a password or a broad token.

1. **Frame it (30 s).** "A public AI assistant wants to call a tool inside our network for one of our users. We never give the assistant a password, and the tool never trusts the assistant's word alone." Point at the banner: everything here is a simulation with mock tokens.
2. **Getting the connector (1 min).** Start with the catalog phase, steps 1 to 4. "Example Corp publishes its connector to the assistant's catalog once. The catalog reviews and lists it. A member adds it from the catalog for free, with nothing to install (UNVERIFIED), and it shows up in their own agent, not signed in yet." Say plainly that step 2 is an organisational step with no protocol, that what a real catalog's review checks is unverified, and that the catalog here is a teaching model, not a claim about any real assistant. Sign-in and consent come on first use, which is the next step. Optional: pick `unlisted_connector` to show that a connector that was never listed cannot be added.
3. **Discovery (1 min).** Run the happy path. Steps 6 to 8: the assistant calls the tool with no token and is told, with a `401`, where the rules are (RFC 9728), then learns which authorization server to use and what it supports (RFC 8414). Nothing was pre-configured except the tool's address.
4. **Authentication (1.5 min).** Steps 9 to 12: the assistant proves it started this request with a PKCE challenge, and names the one resource it wants (RFC 8707). PingFederate owns no users, so it sends the browser to the enterprise IdP, which only authenticates and returns a signed ID token. PingFederate shows consent.
5. **Code and token (1.5 min).** Steps 13 to 15: the code comes back with `state` and `iss`; the assistant checks both. It redeems the code with the plaintext verifier and receives a short-lived token whose audience is the gateway only.
6. **On behalf of the user (1.5 min).** Steps 16 to 18: the gateway validates issuer, audience, expiry and scope, then exchanges the token (RFC 8693) for one that names the user, records the gateway as the acting party (`act`), narrows the scope and changes the audience. The private server checks it all again.
7. **Break it on purpose (2 min).** Use the mistake strip. Pick three: `wrong_verifier` (a stolen code is useless), `wrong_audience` (a token is only good at the resource it was issued for), `passthrough` (the private server refuses the user's token). For each, say which actor refused and why.
8. **Honest close (30 s).** "Standards here are cited by RFC number. Which product features exist exactly as drawn, for example CIMD versus DCR or a non-human-identity store, is as described in the proposal and still to be verified against product documentation. The same goes for how a real assistant's catalog reviews and lists a connector."

If asked "is this PingFederate?": no, it is a stand-in that behaves as the RFCs say; use it to explain the pattern, not to prove a configuration.
